# Design notes

## 1. Why typed `assignee` instead of free-form `submitter` string

Today's `permissions.submitter: 'self' | 'role:HR' | 'group:applicant'` is parsed by string convention. It works for hand-written specs but:

- Type system can't catch typos (`'role: HR'` with a space silently fails)
- AI generators have no schema to validate against
- The wizard has no clean way to render an editor — string type makes the UI awkward
- It can't express the half-dozen new resolution shapes (`functional_head`, `functional_members`, `by_amount` candidates)

Reusing `ActorRef` for `assignee` keeps the DSL vocabulary unified — one mental model for "who" across approvals, notifications, and userTasks.

## 2. assignee resolution returns a *candidate set*, not a single user

Approvals and userTasks differ:

- Approval: resolver returns the candidate set; runtime picks one (or all, for collection types).
- UserTask: resolver returns the candidate set; runtime spawns *one* Task with the candidate set attached, and the first member to claim it owns it.

This change does not yet ship the runtime. It only specifies that:

- `assignee` resolves via the same `IActorResolver` that handles approvals.
- The result is a set; userTask runtime semantics ("any one can claim") are documented in the deferred runtime spec.
- An empty resolution result is a structured failure (`FunctionalMembersEmpty`, `RoleEmpty`, etc.) that the runtime should surface for admin intervention, not a silent assignment to nobody.

## 3. functional_members vs role

`functional_members:finance` and `role:finance_clerk` look similar; how do we choose?

| Use `functional_members:<tag>` when | Use `role:<code>` when |
|---|---|
| The team is "everyone in dept X" — defined by org structure, not by RBAC | The team is a curated authorization list maintained separately from org structure |
| Membership churns automatically as people move between departments | Membership requires an explicit RoleAssignment update |
| The dept already has a `function_tag` set during onboarding | You need cross-department membership (e.g., a "purchase reviewers" group spanning multiple depts) |
| Phase A — fast onboarding, no need to manually populate roles | Phase B — fine-grained access control demanded by the customer |

The two coexist; specs may use either. AI guidance in `prompt_template_v1.md`: prefer `functional_members:<tag>` for SME flows where the team mirrors the dept structure (most common in Taiwanese mid-sized manufacturers).

## 4. ViewerRef — separate type from ActorRef?

`ActorRef` is "who acts" (single or set of users). Viewers includes meta-types like `self` (the original applicant for *this* flow instance) and `current_assignee` (whoever is acting on the open task right now). These are *runtime-scoped* — they don't resolve at spec-load time, only at view time given a flow instance.

We could try to fold them into `ActorRef` (`{ type: 'self' }`, `{ type: 'current_assignee' }`) but that:

- Pollutes the approval/assignee resolver, which would need to handle "current_assignee" specially (cyclic — the assignee references itself)
- Breaks the rule that `ActorRef` resolves to a `Set<UserId>` deterministically at given context

So: separate `ViewerRef` discriminated union, with a wrap-an-ActorRef variant for non-runtime cases.

## 5. Migration of legacy permissions.submitter strings

The wizard's `EMPTY_DRAFT` doesn't yet emit `permissions` — it's documented in `spec_schema.md` v1.0 but not actually written by the export. Existing files in `specs-incoming/` were generated by the wizard so they don't carry the old string.

Real migration is therefore very thin:

1. Schema importer: if a userTask has `permissions.submitter` (legacy string), translate per the cheat-sheet:
   - `'self'` → `{ type: 'expr', path: 'submitter', skip_if_initiator: false }`
   - `'role:X'` → `{ type: 'role', code: 'X' }`
   - `'group:X'` → `{ type: 'group', id: 'X' }`
2. Schema importer: if a userTask carries no `permissions` and no `assignee`, default `assignee = { type: 'expr', path: 'submitter', skip_if_initiator: false }`.
3. Old `permissions.viewers` array translates element-wise; each `'self'` / `'manager'` / `'role:HR'` / `'all'` maps:
   - `'self'` → `{ type: 'self' }`
   - `'manager'` → `{ type: 'expr', path: 'submitter.manager', skip_if_initiator: false }`
   - `'role:X'` → `{ type: 'role', code: 'X' }`
   - `'all'` → `{ type: 'role', code: 'authenticated_user' }` *or* simply omit (everyone with a JWT can read)

The importer lives in `bpm-svc/src/Application/Spec/SpecImportService.cs` (alongside the existing v1.0 → v1.1 ActorRef migration).

## 6. Schema version bump v1.1 → v1.2

`spec_schema.md` already moved v1.0 → v1.1 for the ActorRef change. This is v1.2:

- v1.0 → v1.1: ApprovalRule replaced by ActorRef (already done)
- v1.1 → v1.2: UserTask permissions replaced by typed assignee + viewers (this change)
- v1.2 → v1.3: ActorRef gets functional_head / by_amount / title_match / unresolved (the *previous* proposal, technically a different version bump)

The two version bumps are independent — this change can land before or after `extend-actor-and-org-for-ai-routing` without conflict, because they touch different sections of the schema.

To keep the dev branch sane, I recommend landing them in the order:

1. `extend-actor-and-org-for-ai-routing` (more foundational, sets up function_tag / functional_head used here)
2. `extend-usertask-assignee-by-role` (this)
3. `extend-field-types-line-items` (third)

But the proposals themselves don't have a hard ordering dependency in the spec markdown.

## 7. Open questions

- **Should `assignee` always be a single ActorRef, or also support a `collection`** (e.g., "this task requires finance + IT to both fill")? Current design says single; if a flow really needs co-fill, model it as two userTask nodes with a parallel gateway. Revisit if a customer flow can't be expressed.
- **Should viewers default to "everyone the assignee touches" automatically**, so spec authors don't have to remember? Probably yes for v1.3, but v1.2 leaves it explicit so we surface the question. Default `viewers = [{ type: 'self' }, { type: 'current_assignee' }]` is a safe fallback if omitted.
- **Should `functional_members` return cached results** (the spec author confirmed at design-time which depts have which tags)? Or always live-query? I'd argue live-query — function_tag is set during onboarding then changes rarely; live query keeps the org-chart change reflected without spec re-publish.
- **`include_subtree` semantics** — does it expand to *all* descendant depts or just direct children? Default to all descendants (recursive); add `max_depth` later if a customer hits a corner case.
