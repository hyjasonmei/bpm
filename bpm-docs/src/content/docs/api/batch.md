整批同步幾百個使用者時，逐筆打太慢——用 **`POST /odata/$batch`** 一次 request 包多個操作。

## 重要語意：非交易性

`$batch` **不是交易**：逐筆各自成敗，第 37 筆失敗不影響其他 99 筆。回應裡每筆有自己的狀態碼。

這對同步排程反而是優點——搭配 [upsert](/api/org-crud/) 冪等：

1. 整批推
2. 從回應挑出失敗的筆
3. 修資料後**整批重推**（成功過的 upsert 重跑無害）

## 實務建議

- 批次大小控制在合理範圍（數百筆一批），太大難除錯
- 排程收尾記 log：總筆數 / 成功 / 失敗清單——失敗靜默吞掉是同步排程最常見的坑
