# bpm-svc

Backend services for the BPM platform. Two hosts share one solution; both
consume the same `Application` and `Persistence` layers.

```
bpm-svc/
├── src/
│   ├── Domain/         entities, value objects (no project refs)
│   ├── Application/    MediatR handlers, behaviors, abstractions
│   ├── Persistence/    AppDbContext, EF migrations, audit interceptor
│   ├── Api/            ASP.NET Core Web API — used by bpm-ui (frontend)
│   └── Functions/      Azure Functions isolated worker — reserved for
│                        future integrations (BC, schedulers, MCP bridge)
└── bpm-svc.slnx
```

This is the shared scaffold. Per-customer workflow code (e.g. `LeaveWorkflow`,
`PurchaseWorkflow`) is generated by Claude Code from `spec_schema.md` per the
Concierge MVP pipeline (see `../inovation_idea.md` §3).

## Run locally

```bash
# from bpm-svc/

# Build everything. The Functions project's metadata generator targets net8,
# so on a machine with only .NET 10 installed, set this env var to roll-forward.
export DOTNET_ROLL_FORWARD=LatestMajor
dotnet build

# Apply (or update) the SQLite schema. Database file lives at src/Api/bpm.db.
dotnet ef database update --project src/Persistence --startup-project src/Api

# Start the Web API on http://localhost:5290 (used by bpm-ui)
dotnet run --project src/Api

# Start the Functions host on http://localhost:7172 (reserved for later)
# Needs Azure Functions Core Tools: `brew install azure-functions-core-tools@4`
dotnet run --project src/Functions
```

Health: `curl http://localhost:5290/health`

## Database

SQLite for the POC (`Data Source=bpm.db` in `appsettings.json`). Switching to
SQL Server in production:

1. Replace `Microsoft.EntityFrameworkCore.Sqlite` → `…SqlServer`
2. Change the `UseSqlite` call in `Persistence/DependencyInjection.cs`
3. Drop and re-add the migration — SQLite and SQL Server migrations are not
   portable

## Conventions

- Every entity that's persisted inherits `AuditableEntity` (CreatedAt /
  UpdatedAt / CreatedBy populated by an EF interceptor; never set manually).
- Controllers and Functions triggers dispatch only via `MediatR.ISender`. They
  contain no business logic and do not touch `AppDbContext` directly.
- Commands implement `ICommand<T>` (transaction-wrapped via `UnitOfWorkBehavior`);
  queries implement `IQuery<T>` (no transaction).
- Validators run in `ValidationBehavior` before the handler executes.
- Spec-driven workflow code (per-flow state machines) lives under
  `Domain/Workflows/{FlowCode}Workflow.cs` and is added per customer onboarding.

## Why this scaffold matters for the Concierge MVP

When a new customer's `spec.json` arrives, Jason runs Claude Code with the
prompt template (`../prompt_template_v1.md`) against a copy of this repo. The
prompt assumes:

- These five projects exist in this layout
- `AuditableEntity`, `IClock`, `ICurrentUser`, `IUnitOfWork`, `ICommand<T>`,
  `IQuery<T>`, the three pipeline behaviors, and the audit interceptor are
  available
- The `bpm-ui` SPA exists at the sibling path

Claude Code only adds files specific to the spec; it does not modify the scaffold.
