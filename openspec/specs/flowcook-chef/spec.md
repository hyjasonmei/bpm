# flowcook-chef Specification

## Purpose

Define the **chef** service — flowcook's AI pipeline that transforms a submitted spec into concrete workflow implementation under strict skill-defined rules. chef is internal to flowcook (never directly addressable by customer admins), and is the engine behind the `cooking` lifecycle state.

## Requirements

### Requirement: chef pulls from per-customer serial queue

chef SHALL poll the admin queue of `submitted` flows. For a given customer, chef SHALL process at most one flow concurrently. Different customers MAY be processed in parallel.

#### Scenario: Customer queue is serial
- **WHEN** customer X has two submitted flows
- **THEN** chef finishes the first before starting the second

#### Scenario: Two customers processed in parallel
- **WHEN** customer X and customer Y each have a submitted flow
- **THEN** chef MAY work on both at once

### Requirement: chef writes only inside feature folders

chef SHALL write or modify code only under:

- `bpm-svc/features/{CODE}/V{N}/**`
- `bpm-ui/src/features/{CODE}/V{N}/**`

chef SHALL read but not modify:

- `bpm-svc/{Core,Runtime,Bundle,Principal,Sandbox,Application,Api}/**`
- `bpm-admin-svc/**`
- `syncer/**`
- `chef/**` (itself)

#### Scenario: chef tries to edit ProcessRuntime
- **WHEN** chef's generated diff includes a change to `bpm-svc/Runtime/ProcessRuntime.cs`
- **THEN** the change is rejected — chef's skill instructs it not to and human review enforces

### Requirement: Naming convention uses flat prefix

Every class, table, migration, file, and React component generated by chef SHALL be prefixed `{CODE}_V{N}_`. Namespaces SHALL NOT be used for the prefix; the prefix is part of the identifier.

#### Scenario: Generated class
- **WHEN** chef generates the approval handler for code `LEAVE` version 1
- **THEN** the class SHALL be named `LEAVE_V1_ApprovalHandler`
- **AND** the DB table SHALL be named `leave_v1_leave_request`

### Requirement: Each generated version is wrapped in a feature flag

chef SHALL wrap each `{CODE}_V{N}` version in exactly one feature flag named identically (`{CODE}_V{N}`). All entry points (controllers, event handlers, UI routes) SHALL check the flag and short-circuit to no-op / 404 when off.

#### Scenario: Flag flipped off
- **WHEN** config sets `LEAVE_V1: off`
- **THEN** API calls to LEAVE_V1 controllers return 404
- **AND** the LEAVE_V1 form does not render in bpm-ui

### Requirement: chef never hardcodes external values

chef SHALL NEVER hardcode external URLs, tokens, or environment-specific constants. All such values SHALL be referenced via `${var_name}` from `spec.variables` (see `flowcook-wizard` §VARIABLES).

#### Scenario: chef generates HTTP client for ERP integration
- **WHEN** spec.variables declares `ERP_URL`
- **THEN** the generated client reads the URL via the runtime VariableResolver
- **AND** the source code contains no string literal for the URL

### Requirement: chef triggers on-hold on ambiguity

chef SHALL NOT guess when the spec is ambiguous or missing critical information. Instead it SHALL POST to `bpm-admin-svc /api/flows/{id}/on-hold` with the question payload, after which it SHALL stop work on that flow.

#### Scenario: Spec uses "approver" without specifying
- **WHEN** the wizard left an approval node with no APPROVERS step rule
- **THEN** chef SHALL post an on-hold question rather than picking an approver
- **AND** the flow transitions to `on hold` per `flowcook-lifecycle`

#### Scenario: On-hold payload
- **WHEN** chef calls on-hold
- **THEN** the request body SHALL include `iteration_id` and `question` strings

### Requirement: chef re-reads spec.notes on resume

When admin's Resume action causes a flow to re-enter `submitted` from `on hold`, chef SHALL re-pick it and re-read the full `spec.notes` (including its own prior question and the user's answer) before continuing.

#### Scenario: chef sees previous Q + user A
- **WHEN** chef picks a flow that was previously on-hold
- **THEN** the system prompt context includes the complete `spec.notes` history
- **AND** chef uses the answer to disambiguate

### Requirement: chef output for v0 is a bundle push (not PR)

For v0, chef SHALL push the generated bundle to bpm via API. chef SHALL NOT open a git PR. Tech-tier customer PR mode is deferred to v1+.

#### Scenario: v0 happy path
- **WHEN** chef completes cooking
- **THEN** chef POSTs the bundle to bpm
- **AND** flow state transitions `cooking → committed`

### Requirement: chef includes default tests for every artifact

The bundle chef produces SHALL include tests as follows:

- one rendering test per notification template
- one branch test per gateway
- one approve / reject test per approval node
- one happy-path mock test per integration
- form tests per userTask

#### Scenario: bundle missing branch tests
- **WHEN** chef pushes a bundle missing a gateway branch test
- **THEN** the receiving validator in bpm rejects the bundle and chef must redo (this happens automatically — same on-hold mechanism with `action_type = bundle_validation_failed`)

### Requirement: chef skill is the system prompt source of truth

chef's behavior SHALL be defined by a single skill file (system prompt + reference) maintained at `chef/skill/`. The skill SHALL declare allowed paths, naming conventions, flag wrap requirement, variable handling, on-hold protocol, and output format.

#### Scenario: Skill update changes chef behavior
- **WHEN** the skill at `chef/skill/skill.md` is updated and chef restarts
- **THEN** subsequent chef invocations use the new skill content
- **AND** in-flight work is not retroactively re-cooked

### Requirement: chef has no iteration / cost cap in v0

The chef pipeline SHALL NOT enforce a numeric limit on on-hold cycles or a cost cap in v0.

#### Scenario: Tenth on-hold on same flow
- **WHEN** a flow has cycled on-hold ↔ resume nine times
- **THEN** the tenth on-hold is allowed normally
- **AND** flowcook staff may manually intervene if costs become a concern, but the system does not auto-block

### Requirement: chef cannot be invoked by customers directly

Customers SHALL NOT have API access to chef. The only path to invoke chef is via the lifecycle `draft → submitted` Submit action on admin, which enqueues the flow for chef pickup.

#### Scenario: Customer attempts direct chef call
- **WHEN** a customer admin discovers chef's internal endpoint and tries to call it
- **THEN** the call is rejected (chef accepts only requests from the queue puller / admin internal network)
